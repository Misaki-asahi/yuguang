# 第一部分　流程设计

流程分三层来写：**人怎么用**（用户旅程）、**机器怎么跑**（系统运行）、**机器怎么判断**（判定与干预）。三层对齐之后，代码的模块边界基本就自动出来了——后面第三部分的分层架构，只是这三条流程的物化结果。

需要先说清一件事：这个工具真正的难点不在"能不能截到屏"，而在**"截到屏之后，凭什么说我在摸鱼"**。第一部分的第 3 节会用一整节处理这个问题，因为它是整个产品成不成立的分水岭。

## 1 一天是怎么过的：用户旅程

### 1.1 场景设定

以最常见的自学者场景走一遍（写论文、备考、做副业都同理）：

| 时间 | 发生什么 | 系统在后面做什么 | 用户感知到什么 |
|---|---|---|---|
| 08:05 | 开机 | 随开机自启，托盘出现，小桌宠缩在右下角贴边半隐藏 | 多了一个图标，一个会动的小东西 |
| 08:10 | 想干活了 | 点托盘 → 弹"今天要做什么"，填 1～3 条目标 + 预计时长 | 30 秒填完，开始计时 |
| 09:00–12:00 | 写论文 | 每 5 秒记窗口，每 10 分钟截一张图，每 15 分钟送一批给模型 | 几乎无感，CPU 占用可忽略 |
| 10:37 | 手滑点开 B 站，刷了 3 分钟 | 元数据已经认出浏览器 + 视频站，判定离题，冷却期已过 | 桌宠探头："说好的文献综述呢？"5 秒后自己缩回去 |
| 10:38 | 选择"我就歇 5 分钟" | 记一次干预，进入休息模式，10 分钟内不再打扰 | 桌宠点头，安静下来 |
| 12:00–13:30 | 吃饭、午睡 | 键鼠无输入超过 5 分钟 → 标记 idle，不截图 | 什么也没发生 |
| 22:00 | 该复盘了 | 汇总当天所有时间块，渲染 HTML，用浏览器打开 | 一张时间账单：哪儿深工作、哪儿被切碎、哪儿纯消耗 |
| 22:15 | 觉得"14:00–15:30 说我在无目的浏览是错的" | 点"这其实是在查资料" → 写入纠错表 → 生成一条规则 | 这一条下次同类不再误判 |
| 次日早上 | 打开新一天的日报 | 顶部多一行"比昨天多专注 47 分钟" | 有一个可比的锚点 |

整个白天，用户主动操作只有两次：早上声明目标、晚上看日报。其余全是后台静默完成——这是这套设计能长期活下去的前提。任何需要用户频繁确认的工具，活不过一周。

### 1.2 三个用户故事

- **作为写论文的人**，我希望晚上能看见"今天 8 小时里，真正写东西只有 2 小时 40 分，其余被切成了 37 段"，这样我才知道自己不是不努力，是碎片太多。
- **作为上班族**，我下午三点容易滑坡，我希望那时候有个东西轻轻戳我一下，而不是等我晚上看账单后悔。
- **作为容易自我欺骗的人**，我希望这个工具的判断有证据、能被我推翻——它说我在摸鱼时，我能点开那几张截图看看它到底看到了什么。

### 1.3 首次使用（Onboarding，目标 5 分钟内跑通）

后续所有体验都压在第一次上。向导只做四屏，不做引导动画：

| 屏 | 内容 | 目的 |
|---|---|---|
| 1 | 选隐私档：全本地 / 脱敏上云 / 只记元数据 | 先解决"你敢不敢用" |
| 2 | 展示"它会看到什么"：真实截一张屏，标出会被发送的区域 | 消除恐惧，比任何文案都有效 |
| 3 | 声明今天的目标（可跳过） | 建立"目标锚定"习惯 |
| 4 | 试跑 10 分钟 → 弹出 5 条自动识别结果，让人打勾或改 | 当场校准，建立信任 |

第 4 屏是关键：**让用户在第一天就纠正它 10 次**，比跑一个月再纠错有效得多，因为前 10 次纠错会直接变成规则和提示词里的样例。

### 1.4 目标声明的三种形态

判定"是否偏离"必须有一个参照物，这个参照物就是目标。三种输入方式按成本从低到高：

| 形态 | 输入成本 | 判定准确度 | 适用 |
|---|---|---|---|
| 会话式（推荐） | 一句话 + 时长 | 高 | 25～90 分钟的专注块，MVP 只做这个 |
| 日程式 | 从待办/日历导入 | 中 | 一天有明确排程的人，P2 |
| 无目标（仅记录） | 零 | 低（只分类，不判定） | 出差、开会、探索性工作 |

> 设计取舍：MVP 不做日程式。原因很简单——把"目标"简化成一句话，开发者省掉一整个日历模块，用户省掉一次配置，而判定准确度反而更高，因为一句话比一条日程标题更贴近真实意图。

## 2 机器怎么跑：系统运行流程

### 2.1 进程与线程模型

单进程，五条线程。不用多进程，因为跨进程传截图和数据不值得，而 Python 的 GIL 在这里不是瓶颈——瓶颈是网络 IO 和磁盘。

| 线程 | 周期 | 职责 | 阻塞风险 | 对策 |
|---|---|---|---|---|
| 采集循环 | 5 秒 tick | 读前台窗口、按需截图、落库 | 截图偶发卡顿（游戏全屏） | 限时 2 秒，超时丢弃本帧 |
| 分析 worker | 15 分钟一批 | 组批、调模型、解析、写库 | 网络超时 30 秒 | 重试 2 次后降级为规则结果 |
| UI 主线程 | 事件驱动 | 托盘、桌宠、面板 | Qt 必须在主线程 | 所有耗时活儿丢给上面两条线程 |
| 日报生成 | 每日一次 | 聚合、渲染 HTML、打开浏览器 | 万级数据渲染 | 独立子进程，失败不影响主程序 |
| 看门狗 | 60 秒 | 检查采集心跳、内存 | 自身不能死 | 由系统计划任务兜底重启 |

### 2.2 主运行流程

图 1 描述的是程序从开机到日终的完整生命周期。注意左侧那条虚线：它是**主循环**，除了"满 15 分钟"和"22:00 到了"这两个出口外，其余所有分支都回到采集，不打断循环。

[[fig:assets/fig2_flow.png|图 1　系统主运行流程（单日生命周期）]]

| 步骤 | 失败会怎样 | 处理方式 |
|---|---|---|
| 载入配置 | 配置损坏 | 用内置默认值重建，旧文件改名备份 |
| 声明目标 | 用户跳过 | 进入仅记录模式，日报照出，但不判定、不提醒 |
| 采集 | 截图抛异常 | 只记元数据，样本标 shot_failed=1 |
| 批分析 | API 全挂 | 标记该批次 pending，1 小时后重试；超过 24 小时则只保留元数据 |
| 聚合 | 数据缺失 | 跳过空洞，时间轴留灰段，不猜测 |
| 干预 | 桌宠窗口异常 | 降级为托盘气泡，保证提醒通道不断 |
| 日报 | 渲染失败 | 退化为纯文本摘要，写到 reports/*.txt |

### 2.3 采集子流程

伪代码比文字更准确，下面是主循环的骨架：

```python
loop every 5s:
    win  = get_foreground()            # 标题 / 进程名 / PID
    idle = idle_seconds()              # GetLastInputInfo
    if idle > 300:        mark_idle(); continue
    if is_sensitive(win): store_meta_only(); continue      # 敏感应用不截屏
    if is_fullscreen_video(win): pass                       # DRM 内容截出黑屏，跳过截图
    if now - last_shot > 600s:         # 每 10 分钟一张，切窗口不补拍
        img = grab_screen()            # mss，主屏，失败则跳过
        if not near_duplicate(pHash(img)):                   # 汉明距离 <= 6 视为同帧
            save_jpeg(img, quality=70, max_side=1280)
            insert_sample(win, shot_path)
    insert_meta(win)                    # 元数据永远记，比截图便宜两个数量级
```

三个不显眼但决定成败的细节：

1. **元数据永远记录，截图可以失败。** 窗口标题 + 进程名足以区分 80% 的场景，这条数据几乎零成本。
2. **去重仍然要做。** 60 秒采样时，打字场景下有一半的帧和上一帧几乎一样；改成 10 分钟一张后重复率明显下降，但这道检查是零成本的保险，看视频、挂机时依然管用。
3. **idle 不算浪费。** 人不在电脑前，不该被记成刷手机——这是最招人恨的误判之一。

### 2.4 分析子流程

每 15 分钟一次，一次处理一个批次：

| 环节 | 输入 | 输出 | 耗时预算 |
|---|---|---|---|
| 组批 | 最近 15 分钟的 sample 中 picks=1 的 1～2 张 + 元数据序列 | 一个批次对象 | < 50ms |
| 构造上下文 | 批次 + 当前目标 + 上一批结论（不超过 80 字） | 一次请求体 | < 10ms |
| 调用模型 | 请求体 | JSON 文本 | 3～15s |
| 校验 | JSON 文本 | 结构化 segments | < 5ms |
| 落库 | segments | analysis 行 | < 10ms |
| 触发聚合 | 当日新段 | block 更新 | < 200ms |

失败路径单独说：超时重试两次，仍失败则把整批标为 `pending`；如果连续三个批次失败，自动切到"只记元数据"并弹一次系统通知——**宁可降级，不能假装一切正常**，否则次日拿到一份错误的时间账单比没有更糟。

### 2.5 日终复盘子流程

22:00 触发，或者"最后一个目标结束 30 分钟后"触发（晚间工作的人不该等到第二天）。

1. 汇总当日 sample → analysis → block，补齐被跳过的空洞（灰段）。
2. 计算五项指标（见 12.3），生成一句话总结。
3. 渲染 HTML，写入 `reports/YYYY-MM-DD.html`，`start` 打开浏览器。
4. 归档当天的截图到 `shots/YYYY-MM-DD/`，按保留策略清理更早的目录。
5. 生成次日建议，写入数据库，第二天早上弹一次（只弹一次）。

## 3 怎么判断"摸鱼"：判定与干预流程

### 3.1 先把问题定义清楚

"摸鱼"不是一个状态，是一个**关于意图的判断**。同一个动作，在赶稿时是摸鱼，在查资料时是工作。所以判定必须带三个输入：

> 偏离 = f（当前目标，当前活动，持续时长，上下文）
>
> 其中：当前活动 = 类别（来自元数据 + 截图）+ 置信度 + 证据；
> 持续时长 = 该活动连续未改变的分钟数；上下文 = 今天已完成多少、现在几点。

不追求给"摸鱼"打一个百分制分数——分数会诱发自我欺骗（"我才 62 分，还好"）。只用三档结论：**在任务上 / 疑似离题 / 明确离题**。三档的好处是每档对应一个明确的动作：不管、记录、提醒。

### 3.2 判定决策流程

图 2 是一条"全否才退出"的判定链。任何一环判否，都立即退出并只记录，不打扰。这样设计的目的是把误报率压到接近零——**宁可漏报，不可误报**，因为漏报只是少提醒一次，误报会让用户直接卸载。

[[fig:assets/fig3_decide.png|图 2　单次离题判定决策流程]]

### 3.3 规则与阈值

| 规则 | 条件 | 默认值 | 可调 | 说明 |
|---|---|---|---|---|
| 会话门控 | 无进行中的专注会话 | — | 否 | 不在会话内永不提醒 |
| 豁免名单 | 会议软件 / 白名单应用 / 标题含关键词 | 空 | 是 | 命中即放过并记录 |
| 元数据判定 | 进程或域名命中娱乐规则表 | 见附录 B | 是 | 最高优先级证据 |
| 截图判定 | 元数据无结论时，VLM 置信度 | ≥ 0.7 | 是 | 低于阈值只记"疑似" |
| 持续时长 | 离题连续时长 | ≥ 3 分钟 | 是 | 防误触 |
| 冷却期 | 同一触发源两次提醒间隔 | 10 分钟 | 是 | 防轰炸 |
| 日上限 | L3 级提醒每日次数 | 5 次 | 是 | 防脱敏 |
| 休息豁免 | 用户主动选"休息一会儿" | 10 分钟 | 是 | 尊重人的节奏 |
| 空闲豁免 | 键鼠无输入 | > 5 分钟 | 是 | 人不在，不算摸鱼 |

阈值的取值逻辑：3 分钟是因为短于 3 分钟的切换大多是无意识的顺手点击（查个单词、看一眼消息），提醒了只会烦人；10 分钟冷却是因为人的注意力恢复需要时间，提醒太密会让提醒本身变成干扰源。

### 3.4 干预分级

| 等级 | 形式 | 打扰度 | 触发条件 | 当日上限 |
|---|---|---|---|---|
| L0 | 只记录，不出声 | 无 | 默认 | — |
| L1 | 托盘图标变色 + 无感小气泡 3 秒 | 极低 | 首次判定离题 | 不限 |
| L2 | 桌宠从边缘探头说一句话，5 秒后缩回 | 低 | L1 后 2 分钟仍离题 | 12 次 |
| L3 | 桌宠走到屏幕中央，轻音效，需要点一下 | 中 | L2 后 3 分钟仍离题 | 5 次 |
| L4 | 全屏半透明遮罩 5 秒 | 高 | 仅手动开启"狠人模式" | 2 次 |

默认只用 L1、L2。L3 开始有侵入感，L4 属于自虐型功能，做出来但默认关闭——**把选择权交给用户，把默认值留给自己**（默认值才代表产品态度）。

### 3.5 升级、降级与自动降权

- **升级**：2 分钟（L1→L2）、3 分钟（L2→L3）。每次都要求"活动仍未改变"，否则不升。
- **降级**：用户点"我去干活"→ 重置到 L0 并记一次"成功拉回"；用户点"我就休息会儿"→ 进入 10 分钟休息模式，到点后从 L1 重新开始。
- **自动降权**：某条规则连续 3 天都被用户标为误报，自动把该规则的置信阈值提高 0.1，并在设置里提示"这条规则最近不太准，已调低敏感度"。这比让用户自己去翻配置友好得多。

### 3.6 纠错回流

用户每一次改判都是一条训练数据。三类用途，按性价比排序：

1. **应用级白名单**（最有效，零成本）：用户说"钉钉不算摸鱼"，就直接加进白名单，永久生效。
2. **关键词规则**（有效，低成本）：某类窗口标题总是被误判，生成一条 `标题包含 X → 归为 Y` 的规则。
3. **提示词样例**（中等，低成本）：把纠错的内容追加进本地 few-shot 样例，下次请求时一并发送。

**不做在线微调**：样本量不够、成本高、可控性差，个人工具完全没必要。

## 4 异常与降级

| 异常 | 现象 | 影响 | 降级策略 |
|---|---|---|---|
| 断网 | API 不可达 | 分析停摆 | 元数据照记，批次排队，恢复后补跑（保留 24 小时） |
| 限流 429 | 请求被拒 | 批次失败 | 指数退避，最长 10 分钟，期间降频到 30 分钟一批 |
| 全屏游戏 | 截图正常但无分析价值 | 无 | 元数据已足够判定，跳过截图省费用 |
| DRM 视频 | 截图为黑屏 | 模型看不懂 | 黑屏检测 → 标记，改用元数据判定 |
| 数据库锁 | 写失败 | 丢样本 | WAL 模式 + 写队列重试 3 次，仍失败则落盘 jsonl 待补 |
| 程序崩溃 | 进程退出 | 数据断档 | 系统计划任务每 5 分钟检查心跳，超 10 分钟未更新则重启 |
| 远程桌面切换 | 分辨率突变 | 截图异常 | 重新初始化截图器，丢弃首帧 |
| 多显示器 | 只截主屏 | 漏掉副屏活动 | MVP 只截主屏，元数据覆盖全屏窗口，够用 |
| 系统 DPI 缩放 | 截图区域偏移 | 图不对 | 进程启动时声明 DPI 感知，按物理像素截取 |
